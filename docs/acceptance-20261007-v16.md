# Google Calendar 最小権限への切替

## 原因
OAuth公開状態がTestingで、テストユーザー以外が403 access_deniedになった。旧 calendar.events は全カレンダーの予定の表示・編集を許可する機密スコープだった。

## 実装
- calendar.app.created と openid だけを要求し、include_granted_scopes=false を設定。
- メインカレンダーへのAPI呼出しと calendarList 一覧取得を廃止。
- 本人が反映ボタンを押した時だけ「ふくる」専用カレンダーを作成。本人確認はGoogleに委ねる。
- GoogleのsubをクライアントIDとともにSHA-256化した対応キーと、専用カレンダーIDのみを本人のレコードに保存。トークン・メール・Googleプロフィールは保存しない。
- キーは認証証明に使わない。アプリのログイン・CSRF、Google側のスコープ、専用カレンダー識別情報、イベント所有タグを確認。
- Googleアカウント切替、カレンダー削除後の再作成、再連携、ETag、予定変更、取消注記、ダイアログを閉じた後の停止に対応。
- イベント詳細と予定一覧を同じモジュールへ統合。詳細からの単一イベント追加で他イベントを取消にしない。
- 個人データ取得・アカウント削除の対象にカレンダー対応キーを追加。
- 旧メインカレンダーの予定は読み取らず変更もしない。

## 確認
- Rust 63件成功、Windowsのdev build成功。
- JavaScript構文チェック、旧Calendarの更新・取消検証成功。
- 新Calendar UI/API境界検証: 最小権限、広いスコープ拒否、primary/listに非アクセス、許可後の反映確認、Googleアカウント切替、専用カレンダー再利用、ダイアログ終了、トークン非永続化。
- Lifecycleの期限停止回帰検証成功。
- 制限環境のループバック接続で既存の通信テストが失敗したため、承認済みローカルTCP実行で63件すべて成功を確認。

## 本番設定と実機確認
Google Cloudでは calendar.app.created と openid が非機密に分類され、機密・制限付きスコープがない保存前の構成を確認。設定保存、OAuth Production公開、本番ソース反映と本人のGoogle許可・実予定反映確認はこの記録作成時点では未完了。

Google Workspaceの管理者によるアプリ利用制限など、各アカウント側のポリシーは引き続き適用される。
